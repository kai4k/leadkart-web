# Backend checklist for leadkart-go

What the web BFF (`leadkart-web`, SvelteKit adapter-node) assumes the Go API enforces, verified against `D:\Development\leadkart-go` (branch `feat/orders`, commit `1993385`) on 2026-11-18. File references are paths inside the Go repo.

## Fix first (security)

| #   | Gap                                                                                                                                                                                                                                                                                                                                  | Where                                                                                                                                                                                                                      |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | **Identity routes have no permission check.** Users, roles, role permissions, permission overrides, manager changes, tenant profile / statutory / contact / settings / preferences and the tenant audit feed require authentication only. Any tenant member can grant themselves any role or permission by calling the API directly. | `internal/identity/ports/http.go:98-109`, `:129-171`, `:260`. Wrap in `RequirePermission` with `identity.users.*`, `identity.roles.*`, `identity.tenants.*`. Add an arch test that fails on authentication-only mutations. |
| 2   | **`X-Tenant-Id` is read nowhere.** Operator scope has no server-side effect; tenant context comes only from the JWT `tenant_id` claim. ADR 0039 plans the header (platform callers only, 403 `ambiguous_scope` on unscoped mutations) but it is not built. Path-versus-header precedence is undefined.                               | `internal/common/authn/authn.go` (`RequireAuth`), `internal/common/tenancy`                                                                                                                                                |
| 3   | **No grace window for a re-presented refresh token.** A consumed token revokes the whole family immediately. Two BFF instances (or two tabs racing across instances) presenting the same token end the session. `config.Refresh.GraceWindow` is validated but never used.                                                            | `internal/identity/domain/refreshtoken/family.go` (`Rotate`), `internal/identity/app/command/refresh.go`                                                                                                                   |

| 6   | **Account enumeration.** Lockout (423) happens only for real accounts and before password verification; the password-reset request returns immediately for unknown emails but writes to the database for known ones.                                                                                                                 | `internal/identity/app/command/login.go:363`, `request_password_reset.go:88-101`                                                                                                                                           |

## Holds today

- Every 401 from the authentication middleware carries `WWW-Authenticate`; credential failures (wrong current password, login) do not.
- No 3xx responses from handlers.
- Capabilities (`GET /auth/me/capabilities`) describe the caller from JWT claims and ignore `X-Tenant-Id`.
- Logout revokes the whole refresh-token family; refresh failures answer a uniform 401 `refresh_rejected`.
- Login runs a dummy password verification for unknown emails and returns the same `invalid_credentials`.
- Money is integer paise (`*_paise`) and GST integer basis points throughout the DTOs.
- Session `device_label` falls back to `User-Agent`; the web will forward the browser's `User-Agent` and client IP (Phase 1c).
